## Rules

1. Nothing is invented. Every feature, endpoint, screen and table must be traceable to an HU, RF, RNF or CU. Reference the IDs in commit bodies and code comments where useful.
2. Anything not defined in the documentation is marked `[TO BE DEFINED]`. Never pick a technology, library or business rule silently: list the options with their trade-offs and ask.
3. All code, identifiers, comments, commits and technical docs are in English. Identifiers use the naming already defined in the data model (snake_case in the database).
4. Commits follow Conventional Commits, one commit per logical change. Scopes: `backend`, `web`, `mobile`, `docs`, `chore`.
5. Never commit secrets. Every secret goes in a `.env` file listed in `.gitignore`, with a committed `.env.example` that has the variable names and no values.
6. The development machine runs Windows. When a command differs between PowerShell and Git Bash, give both versions.
7. Never run commands that delete work or rewrite Git history without explaining first what will be lost.
8. Do not modify the course framework folders at the repository root (`agents/`, `config/`, `core/`, `evaluations/`, `interfaces/`, `skills/`, `tools/`) or `docs/architecture.md` and `docs/manifest_schema.md`.

## Repository structure

One repository with a separate folder per application. The web app and the mobile app are independent projects; both consume the backend REST API and real-time channel.

```
FastRouteCO/
├── backend/        Node.js + Express API, business modules and routing engine
├── web/            React web panel (Platform Administrator, Company Administrator, Logistics Supervisor)
├── mobile/         React Native app (Driver, Android and iOS)
├── docs/           Existing documentation (do not restructure)
├── opencode.json   MCP configuration
└── README.md
```

### Cloudinary (evidence photos)

- Stores the photos the driver takes when confirming a delivery or pickup (RF16, HU-15).
- The database stores only the photo URL in `evidence_photos.photo_url`, never the image (RF16).
- The Cloudinary API secret lives only in the backend. The mobile app uploads using a signature generated by the backend, so the secret never reaches the device.
- Offline, the photo is kept on the device and uploaded during synchronization, keeping the actual capture time in `captured_at` (RF17, RNF07, HU-36).

### Phase 0 — Setup (decisions already taken)

These decisions were reviewed and approved. Do not reopen them; if one becomes a problem, explain why and ask before changing it.

| Area | Decision |
|---|---|
| Language | TypeScript in backend, web and mobile |
| Monorepo | pnpm workspaces (`backend`, `web`, `mobile`), no Turborepo; `packageManager` with an exact pnpm version |
| Shared packages | None for now; a shared types package is created in Phase 1 if a real API contract needs it |

| Background GPS | `expo-location` with `expo-task-manager` |
| Authentication | JWT with refresh token (RNF04) |
| Real-time channel | Socket.IO |

| Local infrastructure | Docker Compose with PostgreSQL, Redis and Neo4j (`docker compose`) |
| Testing | Vitest in backend and web, `jest-expo` in mobile. Test scripts pass when there are no tests yet |

Deliverables: the three projects running, Docker Compose services healthy, the initial Prisma migration applied, `.env.example` files in `backend/`, `web/` and `mobile/` without secrets, CI green and a README section explaining how to run each app (including the API URL for the Android emulator and physical devices).

### Phase 1 — Access, companies and users

Decisions already taken (do not reopen them; if one becomes a problem, explain why and ask before changing it):

| Area | Decision |
|---|---|
| First Platform Administrator | Created with the CLI command `pnpm db:seed:admin`; no credentials stored in the repository |
| Sessions | JWT access token (15 min) and refresh token (7 days) with rotation. Refresh tokens stored in `refresh_tokens` as a SHA-256 hash, with `replaced_by` to detect reuse |
| New users | No public sign-up. New users (Company Administrator, supervisor, driver) receive an invitation email with a link (`${WEB_APP_URL}/set-password?token=...`) to define their own password. Invitations are stored in `user_invitations` as a SHA-256 hash, expire after 72 hours and can be resent by the administrator who created the user. Passwords are never sent by email |
| Passwords | bcrypt; minimum 10 characters; no forced expiration. `users.password_hash` is NULL until the invitation is accepted, and login is rejected while it is NULL |
| Deactivation | Inactive users and users of inactive companies cannot log in; deactivating a user or a company revokes their refresh tokens. Companies are never deleted (HU-20 CA04) |
| Permissions | Drivers are managed by the Logistics Supervisor and the Company Administrator (HU-27) |
| Web components | shadcn/ui with Tailwind CSS, themed with `docs/design/DESIGN.md` |
| Design references | `docs/design/phase-1` gives style and layout only; fields and actions come from the HU, RF and data model |
| Out of scope | "Forgot password" is not in the user stories and is not built in Phase 1 |
| Tests | Each step includes its own tests; multi-company isolation tests (RNF09) start with the company endpoints. Tests use their own configuration and never read `.env` |

Steps: (1) backend authentication, (2) Platform Administrator: companies and Company Administrators, (3) Company Administrator: company, branches, supervisors and drivers, (4) seed data, (5) web design system, (6) login and set-password screens, (7–12) web screens for companies, company detail, my company, branches, supervisors and drivers. Each step is reviewed and approved before the next one.

## Rules

1. Nothing is invented. Every feature, endpoint, screen and table must be traceable to an HU, RF, RNF or CU. Reference the IDs in commit bodies and code comments where useful.
2. Anything not defined in the documentation is marked `[TO BE DEFINED]`. Never pick a technology, library or business rule silently: list the options with their trade-offs and ask.
3. All code, identifiers, comments, commits and technical docs are in English. Identifiers use the naming already defined in the data model (snake_case in the database).
4. Commits follow Conventional Commits, one commit per logical change. Scopes: `backend`, `web`, `mobile`, `docs`, `chore`.
5. Never commit secrets. Every secret goes in a `.env` file listed in `.gitignore`, with a committed `.env.example` that has the variable names and no values.
6. The development machine runs Windows. When a command differs between PowerShell and Git Bash, give both versions.

8. Do not modify the course framework folders at the repository root (`agents/`, `config/`, `core/`, `evaluations/`, `interfaces/`, `skills/`, `tools/`) or `docs/architecture.md` and `docs/manifest_schema.md`.

### Phase 2 — Orders, routes and routing engine

Decisions taken:

| Area | Decision |
|---|---|
| Geocoding | Self-hosted Nominatim in Docker Compose, importing the Tolima extract for development. Backend access goes through `backend/src/lib/geocoding.ts`; the production provider is decided with hosting (Phase 7). |
| Address fallback | A failed geocoding request does not block order registration when the service is unreachable (RNF08): the order is stored without coordinates and reported as not geocoded. An address with no result in Nominatim is rejected as invalid (HU-28 R01). |
| Order assignment | An order is assigned by adding it to a driver's route for a date (`route_stops`), the only driver relation available in the data model. The order becomes `assigned`; cancelling it removes the stop and renumbers the route. |
| Driver suggestion | Only active, available drivers of the company are suggested, ranked by distance from their last known route location to the order address, then by fewest pending stops, then by name. |
| Routing engine | Neo4j with APOC Dijkstra over the imported Ibagué road network. If Neo4j is unavailable or no path exists, the backend falls back to an approximate straight-line distance (RNF08). |
| Road network import | A backend script downloads the Ibagué bounding box from the Overpass API and loads the drivable ways into Neo4j; runtime routing never calls external services. |
| Optimization algorithm | Deterministic nearest-neighbor construction followed by 2-opt improvement. The matrix is built from each point to all the others with one Neo4j Dijkstra call per source, so it is asymmetric (one-way streets); 2-opt recalculates the full cost of the reversed segment. The path starts at the driver start point and ends at the last stop, without returning to the start. Processing time (matrix plus algorithm) is measured against RNF01 and stored with total distance and estimated duration in `route_optimizations`. Urgent priority and the maximum number of orders per route remain `[TO BE DEFINED]`. |

- Order registration with OpenStreetMap geocoding (RF04, RF15, HU-28).
- Driver suggestion and order assignment (RF05, HU-29).
- Route creation per driver and day (RF01, HU-06).
- Load the Ibagué road network from OpenStreetMap into Neo4j and calculate paths with Dijkstra (RF15).

### Phase 3 — Plans, credits and payments

Decisions taken:

| Area | Decision |
|---|---|
| Wompi checkout | Hosted checkout at `https://checkout.wompi.co/p/` with the integrity signature `SHA-256(reference + amount_in_cents + currency + WOMPI_INTEGRITY_SECRET)`. Subscription, credit package, module and pay-per-use membership purchases return a checkout URL. |
| Payment reference | Wompi receives `payment.id` as the reference prefix because `payments` has no metadata column: `<paymentId>\|subscription\|<planId>\|<cycle>`, `<paymentId>\|pay_per_use\|<planId>`, `<paymentId>\|credit_package\|<packageId>`, `<paymentId>\|module\|<moduleId>` and `<paymentId>\|usage\|<usageChargeId>`. The webhook verifies the event checksum, the reference and the amount before applying the purchase. |
| Webhook | Public `POST /api/v1/payments/wompi/events` verifies the `signature.properties` values plus the timestamp with `WOMPI_EVENTS_SECRET`, then applies the payment only while it is pending (idempotent for repeated events). |
| Card registration | The web uses the Wompi widget in tokenization mode. The backend issues a short-lived signed setup token, the form posts `payment_source_token` to `POST /api/v1/payments/wompi/card`, and the backend creates the payment source with the private key. Only the Wompi payment source id is stored in `companies.card_reference` (RNF11). |
| Pay-per-use | The accumulated amount is `optimization_count × price_per_optimization + additional_drivers × price_per_additional_driver`. The driver component is monthly, so it is recalculated instead of added on each optimization. A pending charge locks the usage record to prevent duplicate charges. Previous-month usage is charged lazily on the next billing check or optimization. |
| Spending limit | `companies.monthly_spending_limit` is a fixed COP amount. A null value means unlimited; zero blocks all spending. Warning notification at 80% and blocking at 100%. |
| Early charge threshold | `plans.early_charge_threshold` is a fixed COP amount, not a ratio. Seed value is `null` (not defined and therefore disabled) for every plan until the pay-per-use amount is approved. Subscription plans never charge per optimization or per additional driver. |
| Module eligibility | Add-on modules can be bought on the `Pro` plan or in pay-per-use; modules included in the current plan cannot be bought again. Plan/credit/module prices remain `[TO BE DEFINED]`. |
| Billing dates | Credit resets, renewals and usage periods use Bogotá business dates. Annual plans reset credits monthly; monthly and trial plans do not reset until renewal. |
| Expiration | A trial, subscription or pay-per-use membership expires when its renewal date passes; optimizations are blocked and the Company Administrator is notified. A rejected usage charge expires the pay-per-use subscription and keeps the company data. |
